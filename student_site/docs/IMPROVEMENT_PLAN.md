# План улучшения StudentFlow

**Статус:** выполняется поэтапно. Ниже указаны реализованные части и оставшиеся задачи. Составлен по приложению FastAPI + SQLite + Jinja2.

## Уже сделано в первом проходе

- Регистрация с полем учебной группы, автоматическим входом после создания аккаунта и серверным назначением роли `student`.
- Смена пароля с проверкой текущего; смена хэша инвалидирует старые сессии.
- Общий SQLite rate limiter: 8 попыток на логин и 30 с одного IP за 15 минут; состояние сохраняется и разделяется между процессами на одном файле БД.
- Security headers и безопасная production-конфигурация cookie/секрета; production не стартует без секретного ключа и Secure cookie.
- Поиск администратора по ФИО/логину и фильтры журнала преподавателя; понятные пустые состояния.
- Брендированные HTML-страницы 404 и 500 без вывода исключений в интерфейс.
- Проверяемый SQLite backup через встроенный backup API, включая WAL.
- CI workflow: pytest, Ruff и проверки JavaScript.
- Тесты регистрации, авторизации, поиска, смены пароля, rate limit, error pages и backup.

**Ограничение:** rate limiter общий между workers, использующими один SQLite-файл, но для нескольких серверов с разными БД нужен Redis. Backup-команда умеет хранить последние N дней; периодический запуск настраивается через cron/Task Scheduler по `docs/OPERATIONS.md`.


## Цель

Превратить учебный прототип в понятный и надёжный сайт: основные сценарии проходят без тупиков, каждому типу пользователя видны нужные функции, ошибки объяснимы, а безопасность проверяется не только вручную.

## Приоритет 0 — стабилизировать текущую версию

**Зачем:** сначала гарантировать, что регистрация, вход, навигация и preview не ломаются.

- Проверить в браузере весь сценарий: регистрация → автоматический вход → личный кабинет → выход → повторный вход.
- Проверить вход под всеми ролями и запрет доступа к чужим страницам/оценкам.
- Проверить страницу на узком экране, загрузку CSS/JS/favicon и поведение при обновлении.
- Сделать понятные страницы ошибок 403/404/500 с переходом на доступную страницу.
- Убрать тестовые/нерабочие учётные записи из демонстрационного запуска или явно обозначить, что пароли задаются скриптом.
- Добавить короткую инструкцию «первый запуск» и один надёжный способ создания администратора.

**Готово, когда:** новый пользователь может зарегистрироваться, сразу попасть в кабинет, выйти и войти снова; неверный маршрут не выглядит как поломка сайта; проверки проведены в реальном браузере.

## Приоритет 1 — понятный пользовательский продукт

### Единый интерфейс
- Привести подписи и сообщения к одному языку и стилю (казахский основной, при необходимости — русский переключатель).
- Добавить видимые состояния загрузки/пустого списка/успеха/ошибки.
- Проверить контраст, размеры шрифта, клавиатурную навигацию и доступные подписи форм.
- Упростить регистрацию: подсказки формата логина, требований пароля и причин отказа рядом с полями.
- Сделать адаптивную навигацию и таблицы удобными на телефоне.

### Кабинеты
- **Студент:** профиль, список оценок, средний балл и фильтр по предмету/периоду.
- **Преподаватель:** поиск студентов, фильтр по предмету, подтверждение удаления и удобное редактирование оценок.
- **Администратор:** поиск/фильтр пользователей, явное подтверждение смены роли и защита от удаления последнего администратора.
- Добавить единые страницы профиля и смены пароля.

**Готово, когда:** основные действия доступны из соответствующего кабинета, каждое разрушительное действие требует подтверждения, а пустой аккаунт получает понятное объяснение, что делать дальше.

## Приоритет 2 — усилить безопасность аккаунтов и данных

- ✅ Ограничение входа: 8 ошибок на логин и 30 с IP за 15 минут, ошибки логина/пароля не раскрывают существование аккаунта. Регистрацию дополнительно ограничить от массового создания аккаунтов.
- ✅ Production требует секрет из переменной окружения и Secure cookie.
- ✅ Настраиваемые SameSite cookie; localhost остаётся работоспособным без HTTPS.
- ✅ CSRF-проверки покрыты регрессионными тестами; добавить отдельные отрицательные тесты для каждого нового POST-маршрута.
- ✅ CSP, nosniff, Referrer-Policy и HSTS в production. `frame-ancestors` в production по умолчанию равен `'self'`; доверенные origins задаются через `CSP_FRAME_ANCESTORS`. В development директива опускается для встроенного preview.
- ✅ Смена пароля отзывает прежние сессии; восстановление доступа по подтверждённому каналу остаётся будущей функцией.
- Не отдавать хэши паролей и внутренние ошибки пользователю; журналировать события входа и отказа без паролей и токенов.
- Защитить изменение ролей, запретить случайную потерю последнего администратора и проверять авторизацию на сервере для каждого действия.
- ✅ SQLite backup с целостностью и retention 30 дней; добавлены примеры расписания cron и Windows Task Scheduler и шаги восстановления. Настройку реального расписания на целевом сервере всё ещё нужно выполнить.

**Готово, когда:** есть тесты на перебор/CSRF/роли/доступ к чужим оценкам; секреты отсутствуют в репозитории; резервную копию можно восстановить по инструкции.

## Приоритет 3 — надёжная структура и работа с данными

- ✅ Добавлены версионируемые SQL-миграции в транзакциях; миграции инициализируют новую БД, сохраняют существующие данные и выполняются при старте.
- Выделить слой доступа к данным, валидацию и сервисы ролей; сейчас часть запросов и логики всё ещё находится в одном `app.py`.
- Типизировать модели/ответы, добавить единый формат ошибок и логирование.
- Описать связи и ограничения SQLite (уникальность логина, внешние ключи, индексы); тестировать миграцию на копии базы.
- Оставить параметризованные запросы для всех пользовательских данных; не собирать SQL конкатенацией.
- Разделить конфигурацию разработки, тестов и production; не использовать рабочую базу в тестах.

**Готово, когда:** чистая установка и обновление существующей базы выполняются одной документированной командой, тесты работают на временной базе и исходные данные не меняются.

## Приоритет 4 — тестирование и выпуск

- ✅ `pytest` покрывает регистрацию/вход/выход, роли, CSRF, инъекционные строки, фильтры, миграции, password change и backup.
- ✅ Добавлен Playwright E2E smoke test реального FastAPI сервера на временной базе; CI устанавливает Chromium и запускает его. Локальный прогон в Chromium прошёл, включая регистрацию, смену пароля, роли, фильтр журнала и мобильное меню. Результат удалённого CI пока не подтверждён.
- ✅ CI запускает pytest, Ruff, Playwright E2E и JavaScript-логику. Проверку типов и секретов можно добавить отдельными jobs.
- Проверить production-запуск: HTTPS, переменные окружения, статические файлы, журналы, backup/restore, понятная инструкция отката.
- Настроить мониторинг доступности и ошибок без записи персональных данных в логи.

**Готово, когда:** pull request не проходит без зелёных тестов, а выпуск можно повторить из инструкции на чистом окружении.

## Предлагаемая последовательность

1. **Стабилизация:** ручной браузерный прогон и исправление найденных 404/403/сессий.
2. **UX:** тексты, пустые состояния, адаптивность и завершённые сценарии кабинетов.
3. **Безопасность:** ограничение попыток, конфигурация секретов, security headers, журналирование и резервное копирование.
4. **Данные и архитектура:** миграции, слой доступа к данным, изоляция конфигурации.
5. **Автоматизация выпуска:** E2E + CI + инструкция production.

Рекомендуется брать по одному этапу и завершать его проверяемыми критериями, не добавляя сразу большой набор функций поверх нестабильной основы.
